# Configuration and Task Inputs

## Use the Version-Matched Local Schema

The installed `turbo` package includes `schema.json` (since 2.4.0). Point the
root configuration to it so editor completion and validation follow the
installed package rather than a hosted schema:

```json
{
  "$schema": "./node_modules/turbo/schema.json"
}
```

A package-level `turbo.json` may need a path such as
`../../node_modules/turbo/schema.json`, depending on its depth.

## Choose JSONC Syntax

Use `turbo.jsonc` for JSON with comments (since 2.5.0):

```jsonc
{
  "tasks": {
    "test": {
      // Build dependencies before testing.
      "dependsOn": ["^build"]
    }
  }
}
```

The regular `turbo.json` filename also accepts trailing commas (since 2.6.0),
so a separate `.jsonc` filename is not required merely for trailing commas:

```jsonc
{
  "tasks": {
    "build": {},
  },
}
```

## Anchor Inputs at the Workspace Root

`$TURBO_ROOT$` anchors a task input glob at the workspace root (since 2.5.0),
avoiding paths whose `../` depth varies by package:

```json
{
  "tasks": {
    "build": {
      "inputs": ["$TURBO_ROOT$/important-file.txt"]
    }
  }
}
```

## Extend Workspace Configuration

A package-level `turbo.json` can inherit from another workspace package by
putting that package's name in `extends` (since 2.7.0). `"//"` continues to
mean the root configuration:

```json
{
  "extends": ["//", "web"]
}
```

Local array values replace inherited arrays by default. Put
`$TURBO_EXTENDS$` in an array to retain inherited entries and append local
ones (since 2.7.0):

```json
{
  "extends": ["//"],
  "tasks": {
    "build": {
      "outputs": ["$TURBO_EXTENDS$", ".next/**"]
    }
  }
}
```

## Add Informational Task Descriptions

Task definitions accept a `description` field for human and tool context
(since 2.8.0). It does not affect task execution:

```json
{
  "tasks": {
    "build": {
      "description": "Compiles TypeScript and bundles the application",
      "outputs": ["dist/**"]
    }
  }
}
```

## Defer Input Hashing Until Dependencies Finish

Structured `inputs` objects can defer part of the task hash (since 2.10.0).
Use `mode: "jit"` for files generated by an upstream task. Exclude the same
files from the default input set, then add them back as JIT inputs:

```jsonc
{
  "tasks": {
    "codegen": {
      "cache": false
    },
    "build": {
      "dependsOn": ["codegen"],
      "inputs": [
        "$TURBO_DEFAULT$",
        "!src/generated/**",
        {
          "mode": "jit",
          "globs": ["src/generated/**"]
        }
      ]
    }
  }
}
```

JIT inputs are hashed after the task's dependencies finish.

Use `mode: "dependencyOutputs"` to hash selected outputs of dependency tasks:

```jsonc
{
  "tasks": {
    "check-types": {
      "dependsOn": ["^check-types"],
      "outputs": ["dist/**"],
      "inputs": [
        "$TURBO_DEFAULT$",
        {
          "mode": "dependencyOutputs",
          "globs": ["dist/**/*.d.ts"],
          "from": ["^check-types"]
        }
      ]
    }
  }
}
```

This keeps a downstream task cached when an upstream implementation changes
but the selected public outputs, such as declaration files, do not.

## Enable Future Flags Independently

Future Flags opt into upcoming behaviors under `futureFlags` (since 2.9.0).
Each enabled flag affects the global hash.

- `globalConfiguration` moves formerly top-level global settings under
  `global`.
- `affectedUsingTaskInputs` selects affected tasks by their `inputs` rather
  than selecting every task in a changed package.
- `watchUsingTaskInputs` reruns only tasks whose `inputs` match changed files.
- `filterUsingTasks` resolves filters at task level, using `inputs` for Git
  ranges and the Task Graph for `...` traversal.
- `pruneIncludesGlobalFiles` copies files matched by `globalDependencies` into
  pruned output.
- `errorsOnlyShowHash` includes task hashes when `outputLogs` is
  `"errors-only"`.
- `longerSignatureKey` requires `TURBO_REMOTE_CACHE_SIGNATURE_KEY` to be at
  least 32 bytes.
- `experimentalObservability` enables the OpenTelemetry configuration.

Enable only the behaviors intended for the repository and expect a cache-key
change.

## Configure a Local Microfrontend Proxy

Turborepo can proxy multiple local applications through `localhost:3024`
(since 2.6.0). Put `microfrontends.json` in the parent application, map each
application to its local development port, and add route prefixes only to the
applications that need them. The application without matching routes handles
the remainder:

```json
{
  "$schema": "https://turborepo.dev/microfrontends/schema.json",
  "applications": {
    "web": {
      "development": { "local": 3000 }
    },
    "docs": {
      "development": { "local": 3001 },
      "routing": [
        { "paths": ["/docs", "/docs/:path*"] }
      ]
    }
  }
}
```

Start the configured development tasks with `turbo dev`.
