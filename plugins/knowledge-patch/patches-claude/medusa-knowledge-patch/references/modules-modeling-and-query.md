# Modules, data modeling, catalog, and Query

## Catalog and resource behavior

### External IDs on product taxonomy (since 2.14.0)

Product tags, collections, types, and categories now expose `external_id`, allowing integrations to retain identifiers from an external catalog across these resources.

### Membership behavior for `in` (since 2.9.0)

The `in` operator now applies inclusion semantics instead of treating its input as an equality comparison.

### Open-source Loyalty plugin (since 2.14.0)

The formerly Cloud-only Loyalty plugin is now available as `@medusajs/loyalty-plugin`, providing gift cards and account credits and a base for custom loyalty features. Install it, register it under `plugins`, and run migrations:

```sh
yarn add @medusajs/loyalty-plugin
```

```ts
plugins: [{ resolve: "@medusajs/loyalty-plugin", options: {} }]
```

```sh
npx medusa db:migrate
```

### Product Tag metadata (since 2.10.0)

Product Tags now have a metadata field, and Admin provides controls for creating and editing those metadata values.

### Product-category hook additional data (since 2.6.0)

Product-category workflow hooks now receive the operation's additional data, making that context available to hook handlers.

### Product-collection extension behavior (since 2.8.0)

Admin collection operations now accept additional data, and product collection updates return the updated collection, making both available to extension logic.

## Data models and module links

### `MedusaService` create and update return cardinality (since 2.10.0)

Generated `create` and `update` methods now return one model for a single record input and an array for array or selector-based inputs:

```ts
createT({ ... }): T
createT([{ ... }]): T[]

updateT({ id: "br_1234", name: "Hermes" }): T
updateT([{ id: "br_1234" }, { id: "br_4321" }]): T[]
updateT({ selector: { country_of_origin: "France" }, data: { language: "French" } }): T[]
```

### Application-enforced module-link cardinality (since 2.7.0)

Module links now enforce their declared one-to-one, one-to-many, or many-to-many cardinality when `link.create` runs. With neither endpoint marked as a list both IDs are unique; mark one endpoint with `isList: true` for one-to-many, or both for many-to-many:

```ts
export default defineLink(
  ProductModule.linkable.product,
  { linkable: CustomModule.linkable.customModel, isList: true }
)
```

### Data-model-driven translation settings (since 2.13.0)

Translated custom models no longer belong in the Translation Module's `entities` option. Mark text properties with `.translatable()` instead, then choose the entity fields in the Admin translation-settings view; existing translations remain after the upgrade.

```ts
const Store = model.define("store", {
  name: model.text().translatable(),
  description: model.text().translatable(),
})
```

An entity with any translatable field is automatically exposed for configuration, and tax lines can now participate in translation. Translations remain experimental in this release.

### Product-image links (since 2.8.0)

`ProductImage` is now exported for use in custom module links, enabling extensions such as attaching alt text to product images.

### Soft-delete-aware one-to-one uniqueness (since 2.4.0)

The Data Model API now generates a unique index instead of a unique constraint for one-to-one relations. Uniqueness applies only to non-deleted rows, so a foreign key used by a soft-deleted row can be reused.

## Module services, types, and exports

### Generated container typings for custom modules (since 2.2.0)

In development mode, Medusa inspects valid custom modules registered in `medusa-config.ts` and writes their container mappings to `.medusa/types/module-bindings.d.ts`. IDEs can then infer the service type returned by calls such as `req.scope.resolve("brand")`.

### Inferred inputs for custom-module service methods (since 2.5.0)

The autogenerated create and update methods on custom-module services now infer approximate input types from the module's data model. In this first iteration every inferred property is optional even when the database requires it, so compile-time acceptance does not guarantee that an input satisfies database constraints. Container mappings for core services are now typed against their service interfaces.

### Newly exported extension APIs (since 2.2.0)

Fulfillment schema types are now exported, and the Core Flows package exports `updateTaxRegionsStep` for use when composing custom workflows.

### Refetch utilities take parameter objects (since 2.11.0)

`refetchEntity` and `refetchEntities` no longer take positional arguments. Call them with `{ entity, idOrFilter, scope, fields, options }`; the plural utility also accepts `pagination` and `withDeleted` in that object.

## Query, Index, and search

### Experimental cross-module index queries (since 2.8.0)

The experimental `@medusajs/index` module ingests Products, Product Variants, Prices, and Sales Channels into a central structure for filtering across module boundaries. Install and register it, enable the feature flag, and apply its migrations before starting the server:

```sh
yarn add @medusajs/index
```

```ts
// medusa-config.ts
modules: [{ resolve: "@medusajs/index", options: {} }]
```

```dotenv
MEDUSA_FF_INDEX_ENGINE=true
```

```sh
npx medusa db:migrate
```

Query it through `query.index`; to include a custom linked model, add its property names to `filterable` on that side of the link definition:

```ts
const { data, metadata } = await query.index({
  entity: "product",
  fields: ["id", "title", "brand.*"],
  filters: { brand: { name: "Hermes" } },
})
```

The result count in `metadata` is a PostgreSQL planner estimate rather than an exact `COUNT(*)`, so it can be inaccurate for small data sets. This module is experimental and its API is subject to change.

### Link and query API renames (since 2.2.0)

`remoteLink` and `remoteQueryConfig` are deprecated in favor of `link` and `queryConfig`, respectively, and `remote-query-entry-points.d.ts` was renamed to `query-entry-points.d.ts`. The old APIs still work in this release but are scheduled for removal.

### Logical operators in Index filters (since 2.9.0)

Index queries now accept nested `$and` and `$or` arrays in `filters`:

```ts
const { data: products } = await query.index({
  entity: "product",
  filters: {
    $and: [
      { status: "published" },
      { $or: [{ brand: { name: { $ilike: "%adidas%" } } }] },
    ],
  },
})
```

This release also restores indexing of custom-module entities after a regression.

### Negation operators in Index filters (since 2.10.0)

Index filters now support the `$nin` and `$not` operators in addition to the logical operators introduced in 2.9.0.

### Product-variant search by product fields (since 2.8.0)

Product-variant searches can now match properties of the variant's product, rather than being limited to fields on the variant itself.
