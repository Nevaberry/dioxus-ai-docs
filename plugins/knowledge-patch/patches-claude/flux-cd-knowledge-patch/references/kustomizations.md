# Kustomizations and Reconciliation

## Health and dependency readiness

### Custom-resource health with CEL (since 2.5.0)

Use `Kustomization.spec.healthCheckExprs` for resources that do not expose
standard Kubernetes readiness. Each rule selects an API version and kind and
defines CEL expressions for failed and current states. With waiting enabled,
dependent Kustomizations do not proceed until resources are current.

```yaml
spec:
  wait: true
  healthCheckExprs:
    - apiVersion: cluster.x-k8s.io/v1beta1
      kind: Cluster
      failed: "status.conditions.filter(e, e.type == 'Ready').all(e, e.status == 'False')"
      current: "status.conditions.filter(e, e.type == 'Ready').all(e, e.status == 'True')"
```

CEL expressions in `Kustomization.spec.dependsOn` can extend readiness beyond
the dependency's standard Ready condition (since 2.7.0). Health expressions
can leave `kind` empty to match every resource kind in one API group (since
2.9.0).

### Cancel obsolete health checks (since 2.7.0)

The `CancelHealthCheckOnNewRevision` feature gate cancels an in-progress
Kustomization health check when a newer source revision arrives.

## Deletion and component behavior

`Kustomization.spec.deletionPolicy` controls garbage collection (since 2.5.0).
Use `WaitForTermination` when Flux must wait for every managed resource to be
deleted before allowing the Kustomization itself to disappear (since 2.6.0):

```yaml
spec:
  deletionPolicy: WaitForTermination
```

Set `Kustomization.spec.ignoreMissingComponents` to tolerate Kustomize
components that are absent (since 2.7.0).

## SOPS decryption

SOPS decryption covers Kubernetes Secrets generated by Kustomize components
(since 2.5.0).

Kustomize-controller can use centrally managed Age keys for global SOPS
decryption (since 2.7.0). It can decrypt secrets sealed with the Age
post-quantum cipher and can use Kubernetes Workload Identity to authenticate to
OpenBao or HashiCorp Vault (since 2.9.0).

With the `ObjectLevelWorkloadIdentity` feature gate, a Kustomization can use a
per-object tenant identity for SOPS decryption through KMS services (since
2.6.0).

## Referenced configuration watches

Kustomize-controller can reconcile immediately when any of these referenced
objects change (since 2.7.0):

- `postBuild.substituteFrom` ConfigMaps or Secrets.
- `decryption.secretRef`.
- Either kubeConfig reference form.

Opt in an individual referenced object:

```yaml
metadata:
  labels:
    reconcile.fluxcd.io/watch: Enabled
```

Or configure a controller-wide selector such as
`--watch-configs-label-selector=owner!=helm`.

## Inspect merged substitutions

```shell
flux debug kustomization --show-vars
```

This command shows effective variables after merging inline data and referenced
ConfigMaps or Secrets (since 2.5.0). Secret values appear in clear text; handle
the output as sensitive data.

## Server-side apply control

Kustomize-controller supports custom server-side apply stages to order resource
application explicitly (since 2.8.0).

Use `Kustomization.spec.ignore` to remove selected fields from drift detection
and apply when another controller should own them (since 2.9.0):

```yaml
spec:
  ignore:
    - target:
        kind: Deployment
      paths:
        - /spec/replicas
```

This pattern lets an HPA own `spec.replicas` without Flux continually restoring
the Git value.

## Manifest safety and migration

### Flux CRD substitution protection (since 2.9.4)

Flux CRDs carry the annotation
`kustomize.toolkit.fluxcd.io/substitute: disabled`. This prevents
Kustomization post-build substitution from corrupting CRD schema text that
contains `${...}`.

### Partial image overrides (since 2.9.4)

When a `Kustomization.spec.images` entry overrides only selected image fields,
Flux preserves the remaining fields declared in the source
`kustomization.yaml`.

### Managed-field API versions (since 2.9.4)

Enable `--feature-gates=MigrateAPIVersion=true` to have kustomize-controller
migrate API versions recorded in managed-field entries.
