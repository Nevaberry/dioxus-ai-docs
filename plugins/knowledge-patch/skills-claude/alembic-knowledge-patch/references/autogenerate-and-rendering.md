# Autogenerate and rendering

Use this reference when reviewing generated migration operations, writing a
rewriter or comparator, filtering schemas, or customizing rendered Python.

## Expression and constraint rendering

### Preserve labels in generated indexes

Autogenerate preserves labels on index expressions. PostgreSQL operator classes
that use a label name as their key can therefore render against that label
correctly. Do not strip a labeled expression merely to make generated index code
look simpler. (since 1.15.0)

### Render `UniqueConstraint.deferrable` as a boolean

The `deferrable` value is rendered using its Python representation. Correct
output uses `deferrable=True` or `deferrable=False`, not quoted text such as
`deferrable="True"`. Preserve the boolean type in custom renderers. (since
1.15.0)

### Protect finalized reflected names

Autogenerate applies `Operations.f()` to each reflected constraint and index
name. The wrapper marks a final database name so an active naming convention
does not transform it a second time. This prevents failures in conventions that
use `%(constraint_name)s`. (since 1.16.0)

```python
op.drop_constraint(op.f("uq_account_name"), "account", type_="unique")
```

### Render dialect column sequences as names

Sequence-valued dialect arguments such as `postgresql_include` render contained
`Column` objects as string column names. Generated code should contain valid
names, not Python representations of `Column` instances. (since 1.18.0)

## Custom operation rendering

### Use the configured Alembic namespace

When a custom writer embeds an `ExecuteSQLOp`, autogenerate renders
`Operations.execute()` with the namespace from `alembic_module_prefix`. It no
longer hardcodes `op.`. Custom render tests should assert the configured prefix.
(since 1.16.0)

### Render a rewriter-supplied column rename

Autogenerate rendering considers `AlterColumnOp.modified_name` as of 1.15.2.
A custom `Rewriter` can set this attribute to render the renamed column.
Alembic still does not detect column renames automatically; the recipe must
decide that a rename occurred. (1.15.0 batch)

### Read revision context from detected-diff failures

`AutogenerateDiffsDetected` includes the revision context. Command wrappers can
read that context when turning detected differences into another output format
or report. (since 1.15.0)

## Backend comparison behavior

### Ignore PostgreSQL's added `regclass` cast

For sequence defaults on non-primary-key PostgreSQL columns, autogenerate
ignores a server-added `::regclass` cast. An otherwise unchanged sequence
default should not recur as a diff solely because PostgreSQL added the cast.
(since 1.18.0)

### Compare MySQL ENUM membership, not order

Autogenerate compares individual values in a MySQL `ENUM`. A value present on
only one side produces a diff; changing only the order of the same values does
not. (since 1.18.0)

### Detect named CHECK additions and removals

Named `CHECK` constraints are compared by default through the
`alembic.autogenerate.checkconstraint_byname` plugin. Comparison is name-only:
adding or removing a named constraint produces a diff, while changing its
expression without changing its name does not. (since 1.19.1)

Alembic 1.19.1 also corrects erroneous detections involving column-bound check
constraints. Exclude the plugin from
`EnvironmentContext.configure(autogenerate_plugins=...)` to disable this
comparison.

## Filtered schemas and foreign keys

### Expect placeholder target tables

Autogenerate does not raise `NoReferencedTableError` merely because a foreign
key's target table was excluded by `include_name` or was absent from reflected
schemas. (since 1.18.0)

An `include_object` callback inspecting such a constraint can receive a
placeholder target table. The placeholder carries the target table name,
schema, and referenced columns, but is not a fully reflected table. Restrict
callback logic to that available identity data unless full reflection is known.

## Plugin-based extension

### Register and select autogenerate plugins

The `Plugin` interface supports automatically loaded third-party extensions.
A plugin can register operations and their implementations as well as
autogenerate comparators through `Plugin.add_autogenerate_comparator()`.
(since 1.18.0)

Built-in and third-party comparison plugins are selected for each environment
with `EnvironmentContext.configure(autogenerate_plugins=...)`. Existing add-ons
remain supported and do not have to adopt plugin entry points.
