# CLI, Testing, and Formatting

## Migration, parsing, and checking

### Check and rewrite v0 policy (`1.0-migration`)

Use a v1 binary to expose both syntax and compilation incompatibilities, run
the former strict checks, rewrite into v1 syntax, and lint the result.

```sh
opa check --v0-v1
opa check --v0-v1 --strict
opa fmt --write --v0-v1
regal lint
```

### Parse legacy modules explicitly (`1.6.0`)

Use `opa parse --v0-compatible policy.rego` when a module still uses legacy
syntax. Parsing without the flag applies the current default grammar.

### Check bundles for document conflicts (`1.6.0`)

`opa check --bundle ./bundle` reports an error when a JSON or YAML base document
overlaps a virtual document generated by a rule. Fix the path collision rather
than allowing evaluation order to decide the result.

## Test authoring and execution

### Parameterize data-driven tests (`1.2.0`)

Generate hierarchical named cases by putting the case name in the test rule
head. `opa test` reports each generated case below the rule, so one failure does
not hide the other inputs.

```rego
package example_test

test_concat[note] if {
	some note, tc in {
		"empty": {"a": [], "b": [], "want": []},
		"filled": {"a": [1], "b": [2], "want": [1, 2]},
	}
	array.concat(tc.a, tc.b) == tc.want
}
```

### Expect corrected summaries (`1.3.0`)

Parameterized cases count toward the `opa test` report counter. In non-verbose
mode, the summary lists only failed sub-test cases.

### Control parallel execution (`1.6.0`)

Tests run in parallel by default with one execution thread per available CPU
core. Use `opa test . --parallel=1` for suites that require serial execution.

### Sort JSON results by duration (`1.13.0`)

JSON-format `opa test` results can be sorted by duration to find slow tests.

### Consume streamed results (`1.17.0`)

`opa test` streams individual test-case results. Under `--coverage`, failures
include their complete errors. Parsers must accept incremental results rather
than waiting for one monolithic report.

### Rebaseline source coverage (`1.18.0`)

`opa test --coverage` reports source ranges and tracks inline rule heads and
conjunction expressions. Coverage locations and totals can change even when the
policy behavior is unchanged.

## Output streams and interactive tools

### Correlate `opa exec` by decision ID (`1.2.0`)

`opa exec` includes the decision ID in its output. Preserve it when correlating
execution results with decision logs or traces.

### Read evaluation errors from stderr (`1.9.0`)

`opa eval` writes evaluation errors to stderr. Automation that captures or
parses CLI output must process stderr separately from stdout.

### Debug with YAML input (`1.0.0`)

The debugger accepts YAML directly; a JSON conversion step is unnecessary.

### Allow REPL history migration (`1.19.0`)

The REPL supports bracketed paste, so pasted tab-indented policy is inserted
literally instead of invoking completion. On first use it migrates the default
`~/.opa_history`, or the path selected by `--history`, from the old line format
to JSON Lines in place. Back up the file first if another tool still expects the
old representation.

## Formatting

### Preserve compatibility imports (`1.0.0`)

In v1 mode, `opa fmt` retains `rego.v1` and `future.keywords` imports so modules
can continue expressing their intent to older consumers.

### Discard diffs from affected formatters (`1.4.0`)

The formatter no longer changes string contents or panics on unexpected
comments. Re-run formatting with 1.4.0 or later before trusting a diff produced
by an affected earlier formatter.

### Preserve unchanged file timestamps (`1.13.0`)

`opa fmt` does not overwrite a file when formatting produces no changes, so a
no-op run keeps the modification time.

### Use 1.18.2 for formatting (`1.18.0`)

OPA 1.18.0 incorrectly forced single-item arrays, objects, and sets onto
multiple lines. 1.18.2 restores the behavior in which existing source newlines
choose one-line versus multiline form. The formatter also preserves `with`
clauses after comments in object values and a lone `with` on a closing-bracket
line.

## Building OPA from source

### Meet the initial v1 toolchain floor (`1.0.0`)

Building OPA itself or compiling it as part of a Go integration requires Go
1.22 or newer.

### Match the release toolchain (`1.9.0`)

Use Go 1.25.1 when reproducing OPA 1.9.0 builds.

### Match the later toolchain (`1.12.0`)

Use Go 1.25.5 when reproducing OPA 1.12.0 builds; this replaced Go 1.25.4.

### Match the 1.15 toolchain (`1.15.0`)

Use Go 1.26.1 when reproducing OPA 1.15.0 builds.

### Distinguish distributed and self-built security (`1.17.0`)

OPA 1.17.1 distributed binaries and images use Go 1.26.4 to fix
standard-library vulnerabilities reachable through the HTTP handler and crypto
built-ins. A self-built artifact has the security properties of the Go version
chosen by its builder.

### Use the later security rebuild (`1.19.0`)

OPA 1.19.0 artifacts use Go 1.26.5. OPA 1.19.1 is otherwise identical and uses
Go 1.26.6 to fix standard-library vulnerabilities reachable through the HTTP
handler and cryptographic built-ins. Self-built artifacts again depend on their
selected toolchain.
