# Modules, models, and extensions

## Module services and generated APIs

### Generated container typings for custom modules (2.2.0)

In development mode, Medusa inspects valid custom modules registered in
`medusa-config.ts` and writes their container mappings to
`.medusa/types/module-bindings.d.ts`. IDEs can infer the service type from calls
such as `req.scope.resolve("brand")`.

### Newly exported extension APIs (2.2.0)

Fulfillment schema types are exported. Core Flows also exports
`updateTaxRegionsStep` for custom workflow composition.

### Product workflow inventory input typing (2.3.0)

The `createProductsWorkflow` input type includes `inventory_items`, so
TypeScript callers can supply inventory-item data without casts or type
overrides.

### Inferred inputs for custom-module service methods (2.5.0)

Autogenerated create and update methods on custom-module services infer
approximate input types from the module data model. In this first iteration,
every inferred property is optional even when required by the database, so
compile-time acceptance does not guarantee that database constraints are met.
Container mappings for core services are typed against their service
interfaces.

### `MedusaService` create and update return cardinality (2.10.0)

Generated `create` and `update` methods return one model for a single-record
input and an array for array or selector-based input:

```ts
createT({ ... }): T
createT([{ ... }]): T[]

updateT({ id: "br_1234", name: "Hermes" }): T
updateT([{ id: "br_1234" }, { id: "br_4321" }]): T[]
updateT({ selector: { country_of_origin: "France" }, data: { language: "French" } }): T[]
```

## Data migrations and relationships

### One-time cross-module data migration scripts (2.3.0)

Medusa discovers default-exported files under `src/migration-scripts` in
projects, plugins, and core, then runs them automatically during
`medusa db:migrate`. Scripts have dependency-container access for cross-module
changes. Execution is tracked in `script_migrations` under a table lock, and a
script is skipped on later runs only after it succeeds.

### Soft-delete-aware one-to-one uniqueness (2.4.0)

The Data Model API generates a unique index rather than a unique constraint for
one-to-one relations. Uniqueness applies only to non-deleted rows, allowing a
foreign key held by a soft-deleted row to be reused.

### Application-enforced module-link cardinality (2.7.0)

Module links enforce declared one-to-one, one-to-many, or many-to-many
cardinality during `link.create`. If neither endpoint is a list, both IDs are
unique. Mark one endpoint with `isList: true` for one-to-many or both for
many-to-many:

```ts
export default defineLink(
  ProductModule.linkable.product,
  { linkable: CustomModule.linkable.customModel, isList: true }
)
```

### Data-model-driven translation settings (2.13.0)

Translated custom models no longer belong in the Translation Module's
`entities` option. Mark text properties with `.translatable()`, then choose the
entity fields in the Admin translation-settings view:

```ts
const Store = model.define("store", {
  name: model.text().translatable(),
  description: model.text().translatable(),
})
```

An entity with any translatable field is exposed automatically for
configuration, tax lines can participate in translation, and existing
translations remain after upgrade. Translations are experimental in this
release.

### External IDs on product taxonomy (2.14.0)

Product tags, collections, types, and categories expose `external_id`, letting
integrations retain external-catalog identifiers across those resources.

## Hooks and workflow extension surfaces

### Product-category hook additional data (2.6.0)

Product-category workflow hooks receive the operation's additional data, so
hook handlers can consume that context.

### Stock-location creation hook (2.6.0)

`createStockLocationsWorkflow` exposes a hook for extending stock-location
creation.

### Workflow step results through context (2.7.0)

Workflow implementations can access step results through workflow context,
giving extension logic another way to consume results produced elsewhere in
the workflow.

### Product-collection extension behavior (2.8.0)

Admin collection operations accept additional data. Product collection updates
return the updated collection; both are available to extension logic.

### Exported order utility workflows (2.8.0)

Order-related utility workflows are exported from Core Flows for reuse in
custom workflows.

## Linkable resources and modules

### Direct file uploads (2.8.0)

The File Module and its providers expose the operations needed for direct file
uploads.

### Product-image links (2.8.0)

`ProductImage` is exported for use in custom module links, enabling extensions
such as attaching alt text to product images.

### Open-source Loyalty plugin (2.14.0)

The formerly Cloud-only Loyalty plugin is available as
`@medusajs/loyalty-plugin`. It provides gift cards and account credits and a
base for custom loyalty features. Install it, register it under `plugins`, and
run migrations:

```sh
yarn add @medusajs/loyalty-plugin
```

```ts
plugins: [{ resolve: "@medusajs/loyalty-plugin", options: {} }]
```

```sh
npx medusa db:migrate
```
