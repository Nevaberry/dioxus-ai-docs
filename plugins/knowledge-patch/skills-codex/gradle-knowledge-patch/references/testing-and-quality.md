# Testing, Reports, and Quality Tools

## Configure test discovery

### Explicit inputs for custom `Test` tasks

For the `9.0.0-upgrade`, a newly registered `Test` task no longer inherits the built-in `test` source set's classes and runtime classpath. Configure both explicitly or use JVM test suites:

```kotlin
val test by testing.suites.existing(JvmTestSuite::class)
tasks.register<Test>("otherTest") {
    testClassesDirs = files(test.map { it.sources.output.classesDirs })
    classpath = files(test.map { it.sources.runtimeClasspath })
}
```

A test task with sources and no filters fails when it discovers no tests. Set `failOnNoDiscoveredTests = false` on `AbstractTestTask` only if empty discovery is intentional.

### Non-class JUnit Platform definitions

Since `9.4.0`, a `Test` task can discover definitions handled by a custom JUnit Platform `TestEngine` without a test class. This lets Cucumber run feature files without an empty suite class or extension:

```kotlin
tasks.named<Test>("test") {
    testDefinitionDirs.from("src/test/definitions")
}
```

### Visible framework initialization failures

Since `9.7.0`, TestNG, JUnit 4, and JUnit Platform initialization failures bypass the default granularity filter and appear in console output. Explicitly removing `FAILED` from `testLogging.events` can still silence them. Tooling API and Build Scan consumers can identify them with `TestFailureDetails.isFrameworkFailure()`.

## Configure test frameworks

### Generic Kotlin test dependency from `init`

Since `9.1.0`, Kotlin projects generated by `init` use `org.jetbrains.kotlin:kotlin-test` rather than `kotlin-test-junit5`. The selected test-library variant can therefore follow the configured test runner.

### TestNG thread-pool factories

Since `9.7.0`, `threadPoolFactoryClass` supports TestNG 7.10+, where the class must implement `org.testng.IExecutorServiceFactory`. With TestNG 7.0 through 7.9, it must implement `org.testng.thread.IExecutorFactory`:

```kotlin
tasks.test {
    useTestNG {
        threadPoolFactoryClass = "com.example.MyExecutorServiceFactory"
    }
}
```

## Read built-in test reports

### Assumption reasons

Since `8.14.0`, skipped tests caused by assumption violations include the reason in HTML and JUnit XML reports for JUnit 4, JUnit Platform, and TestNG.

### Timestamp precision

Since `8.13.0`, JUnit XML test-event timestamps use millisecond precision. Consumers must accept values such as:

```xml
timestamp="2024-02-03T12:34:56.789"
```

### Framework hierarchy and output attribution

Since `9.3.0`, HTML reports mirror framework structure:

- Nested classes appear under their enclosing class.
- Parameterized methods own their invocations.
- Suites own their classes.
- Synthetic package containers are removed.
- Standard output and error remain attached to the test that produced them.

Nested-class XML files retain names such as `TEST-OuterClass$InnerClass.xml`; suite XML emits class reports only.

### Aggregate reports preserve sources

Since `9.3.0`, `TestReport` and the Test Report Aggregation Plugin do not merge overlapping structures from different inputs. Each source receives its own HTML tab, preserving attribution when subprojects reuse suite or class names.

### JUnit data and attachments

Since `9.4.0`, Gradle captures JUnit Platform `TestReporter` key-value entries and files, including data emitted during construction, setup, and teardown:

```java
testReporter.publishEntry("browser", "firefox");
testReporter.publishFile(
    "screenshot.svg",
    MediaType.create("image", "svg+xml"),
    file -> {}
);
```

HTML reports add Data and Attachments tabs. XML maps key-value entries to `<properties/>` and files to `[[ATTACHMENT|/path/to/file]]` markers.

### Metadata listeners

Since `9.4.0`, build logic can consume structured metadata without parsing test output:

```kotlin
tasks.named<Test>("test") {
    addTestMetadataListener(LoggingListener())
}
```

The relevant API is `Test.addTestMetadataListener(TestMetadataListener)`.

### Sortable HTML columns

Since `9.6.1`, columns in `Test` HTML reports cycle through sort, reverse sort, and original order when clicked. Tests, Failures, Skipped, and Duration sort descending first; Success rate sorts ascending first.

## Generate reports for custom test infrastructure

Since `8.13.0`, plugin and platform authors can inject `TestEventReporterFactory` and generate Gradle-style binary results and HTML reports for tests outside the built-in infrastructure. Reporters accept timestamped `metadata(...)`, nested `reportTestGroup(...)` groups, and `reportTest(...)` events:

```java
try (TestEventReporter test = testEventReporterFactory
        .createTestEventReporter(
            "custom-test",
            binaryResultsDirectory,
            htmlReportDirectory)) {
    test.started(Instant.now());
    test.metadata(Instant.now(), "engine", "custom");
    test.succeeded(Instant.now());
}
```

## Stream TestKit output

Since `9.3.0`, `BuildResult.getOutputReader()` returns a `BufferedReader`. Process high-volume `GradleRunner` output incrementally and close the reader:

```java
try (BufferedReader reader = result.getOutputReader()) {
    boolean found = reader.lines()
        .anyMatch(line -> line.contains("example build message"));
}
```

Since `9.7.0`, startup `-javaagent:` agents work with TestKit's default daemon mode and Configuration Cache. Dynamically attached agents and embedded mode through `withDebug(true)` remain unsupported; use `-Dorg.gradle.debug=true` for manual debugging.

## Configure ANTLR generation

### Target packages

Since `9.1.0`, `AntlrTask.packageName` sets both ANTLR's `-package` argument and the matching output directory. It supports ANTLR 4 only. Passing `-package` directly is deprecated and becomes an error in Gradle 10:

```kotlin
tasks.named("generateGrammarSource").configure {
    packageName = "com.example.generated"
}
```

### Generated-source tracking

Since `9.1.0`, changing the generated-sources directory updates the related Java source set automatically and wires consumers to depend on source generation.

### Discoverable tasks

Since `9.2.0`, `generateGrammarSource`, `generateTestGrammarSource`, and other ANTLR tasks belong to the `Antlr` group. They appear in normal `./gradlew tasks` output rather than only under Other tasks in `./gradlew tasks --all`.

## Configure quality reports

### PMD formats

Since `9.4.0`, individual `Pmd` tasks can emit CSV, Code Climate, and SARIF. They are disabled by default and must be configured on the task, not the `pmd` extension:

```kotlin
tasks.pmdMain {
    reports {
        csv.required = true
        codeClimate.required = true
        sarif.required = true
    }
}
```

### `@Optional` validation

Since `9.6.1`, `validatePlugins` reports targeted errors when `@Optional` has no input/output annotation or is combined with `@Internal`. Add the relevant input/output annotation, or use `@Internal` alone for an ignored property.

### Default tool versions

For the `9.0.0-upgrade`, defaults changed to Checkstyle 10.24.0, CodeNarc 3.6.0, PMD 7.13.0, JUnit Jupiter 5.12.2, TestNG 7.11.0, and Spock 2.3.

## Configure Groovydoc execution

Since `9.7.0`, `Groovydoc` uses the project's Java toolchain by default and exposes `javaLauncher` for task-specific selection. It runs in a separate worker process; the incubating `maxMemory` property controls that worker's heap:

```kotlin
tasks.named<Groovydoc>("groovydoc") {
    javaLauncher = javaToolchains.launcherFor {
        languageVersion = JavaLanguageVersion.of(21)
    }
    maxMemory = "1g"
}
```

## Verification checklist

- Confirm custom `Test` tasks have both test classes and runtime classpath.
- Exercise empty discovery and framework-initialization failures deliberately.
- Parse JUnit XML with millisecond timestamps, properties, and attachment markers.
- Inspect nested, parameterized, suite, and aggregate HTML structures.
- Close streamed TestKit readers and use the same daemon mode as CI.
- Configure PMD report formats on each task that needs them.
- Remove ambiguous `@Optional` and `@Internal` annotation combinations.
